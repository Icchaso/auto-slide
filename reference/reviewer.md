# 見た目レビュー役への指示書

> 作り手とは**別のエージェント**に、このファイルごと渡して使う（作り手が自分で採点すると甘くなる）。
> レビュー役のモデルは Sonnet 以上を推奨（Haiku の採点精度は未検証。SKILL.md の「モデル別の実測」参照）。

## あなたの役割
描画済みのスライド画像を見て、採点表で点をつけ、**deck.json をどう直すかだけ**を返す。
HTML・CSS・座標・色・文字サイズには触れない（それらは型エンジンが決めている。指示しても反映できない）。

## 渡されるもの
| もの | パス | 見る目的 |
|---|---|---|
| 全枚の一覧 | `decks/<案件>/out/sheet.png` | デッキ全体のリズム・単調さ・明暗 |
| 各スライド | `decks/<案件>/out/NN_<型>.png` | 1枚ずつの採点（**全枚をReadで開く**。一覧だけで採点しない） |
| 中身データ | `decks/<案件>/deck.json` | どの枠に何が入っているか・直す場所の特定 |
| 機械検品の結果 | `decks/<案件>/out/qc-report.json` | 機械が既に見た項目（二重に指摘しない） |
| 採点表 | `reference/rubric.md` | ②デッキ全体 D1〜D21 ／ ③パターン別 P01〜P22 ／ ④日本語組版 |
| 型の枠 | `reference/layouts.md` | 直し方に使える型・枠・文字数上限 |
| 台本 | 依頼時に渡される原文 | 事実の確認（**台本に無い数字・声・金額を足す指示は禁止**） |

## 型 → 採点表のパターン対応
| 型 | パターン | 型 | パターン |
|---|---|---|---|
| cover | P01 表紙 | features | P14 特徴 |
| agenda | P02 目次 | pricing | P15 料金 |
| section | P03 中扉 | testimonial | P16 事例・声 |
| problem | P04 課題提起 | profile | P17 プロフィール |
| message | P05 主張1つ | screenshot | P18 画面紹介 |
| big-number | P06 巨大数字 | photo | P19 写真＋メッセージ |
| bars | P07 グラフ | faq | P20 FAQ |
| compare / table | P08 比較 | summary | P21 まとめ |
| flow | P09 フロー | closing | P22 CTA |
| timeline | P10 ロードマップ | pyramid | P11 階層 |
| matrix | P12 マトリクス | funnel | P13 ファネル |

## 採点の手順
1. `sheet.png` を見てデッキ全体の印象をつかむ（単調か・明暗があるか・図が主役か）
2. 各スライドを開き、対応パターンの項目を **0 / 1 / 2 点**で採点 → そのパターン満点に対する %
   - 共通ゲート（C1〜C7）に1つでも当たる枚は **0%**
3. デッキ全体 D1〜D21 を 0 / 1 / 2 点で採点（目視で判断できない項目は採点しない）
4. **総合点 = スライド平均% × 0.6 ＋ D項目の得点率 × 0.4**（100点満点・整数）
5. 直す指示は**点への効き目が大きい順に最大8件**。1件ごとに deck.json の変更として書く

## 合格ライン
- 機械検品の必須ゲート全合格（qc-report.json の `pass: true`）
- 総合点 **80点以上**、かつ 60%未満のスライドが無い

## 直し方として出してよい変更（これ以外は出さない）
| 種類 `op` | 例 |
|---|---|
| `rewrite` 文言を書き換える | 見出しを言い切りに・長い本文を削る・強調 `*語*` の位置を変える |
| `change-layout` 型を変える | 文章カードの羅列 → compare / flow / bars。変えた型の枠に合わせて中身も全部書く |
| `set` 任意の枠を足す・外す | `highlight` で主役を1つ決める・`takeaway` / `verdict` / `goal` を足す・`lead` を外す |
| `split` 1枚を2枚に分ける | 項目が多すぎる枚 |
| `merge` 2枚を1枚にまとめる | 中身が薄い枚が並んでいる |
| `move` 並べ替える | 同じ型の連続を崩す・暗い面を中盤に入れる |

## 出力（JSON だけを返す。前後に文章を書かない）
```json
{
  "round": 1,
  "total": 84,
  "slideScores": [ { "slide": 3, "layout": "problem", "pattern": "P04", "percent": 92, "worst": "3項目とも同じ形で主役が無い" } ],
  "deckScore": { "got": 36, "max": 42, "misses": ["D10 暗い面が1枚だけ"] },
  "verdict": "revise",
  "changes": [
    { "slide": 3, "op": "set", "path": "highlight", "value": 1, "why": "いちばんの壁を1つに絞るとジャンプ率が出る（P04-3）" },
    { "slide": 8, "op": "rewrite", "path": "title", "value": "確認は迷った行だけで済む", "why": "体言止めで主張が読めない（D2）" }
  ]
}
```
- `verdict` は合格ラインを満たせば `"pass"`、満たさなければ `"revise"`
- `slide` は1始まりの番号（ファイル名の NN と同じ）
- `path` は deck.json のそのスライド内のキー（例: `items[2].body`・`left.items[0]`）
- `value` は**枠の文字数上限に収まる**完成形を書く（上限は layouts.md）。「もっと具体的に」のような抽象指示は禁止
- `change-layout` / `split` のときは `value` に新しいスライドの JSON をまるごと書く

## 作り手（メイン）側のループの決まり
1. `node scripts/build.mjs decks/<案件>` が必須ゲート全合格になってからレビューに回す
2. レビュー前に `deck.json` を `deck.r0.json` として複製しておく（ラウンドごとに r1, r2）
3. 返ってきた `changes` を deck.json に反映 → build → 必須ゲート全合格を確認 → 再レビュー
4. **最大2ラウンド**。2ラウンド目で点が下がったら、**点が一番高かった版の deck.json に戻して**書き出す
5. 最終の点数と残った指摘をユーザーへの報告に書く（「合格です」だけで終わらせない）
